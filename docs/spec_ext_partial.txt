回合制RPG核心戰鬥系統延伸規格

32.資料Schema總體規範

所有正式遊戲內容必須採用資料驅動架構。技能、職業、天賦、裝備、狀態、資源、敵人、效果、觸發條件不得將主要內容邏輯直接硬編碼於UI或戰鬥流程。
資料層與執行層必須分離：
資料層：描述「內容是什麼」。
規則層：描述「規則如何運作」。
執行層：負責「依規則執行」。
顯示層：負責「如何呈現」。
禁止UI直接修改戰鬥核心資料。
禁止內容資料直接控制畫面。
禁止單一技能自行建立專屬戰鬥流程，除非通用系統確實無法表達。
所有Schema應支援版本欄位，以便未來資料遷移。

33.共用資料規則

所有可識別內容原則上支援：
id
version
tags[]
enabled
metadata
id必須永久穩定。正式存檔不得依賴顯示名稱辨識內容。名稱、說明、圖示等展示資料不得作為邏輯識別碼。
引用其他資料時優先使用穩定ID或標籤查詢。
刪除已進入正式版本的ID前必須檢查存檔相容性。

34.職業Schema

概念結構：
ClassDefinition{
id,
version,
tags[],
base_rules,
stat_rules[],
resource_refs[],
core_mechanics[],
skill_access_rules[],
equipment_access_rules[],
passive_effects[],
restrictions[],
ai_metadata
}
core_mechanics必須使用通用Trigger/Effect/Resource/Status系統表達。
不得將職業核心規則散落於多個無關模組。

35.技能Schema

SkillDefinition{
id,
version,
tags[],
target_rule,
costs[],
cooldown_rule,
priority_rule,
hit_rule,
critical_rule,
effects[],
requirements[],
cast_rules,
usage_limits[],
learning_rules,
ai_metadata
}
技能本身描述「何時可以使用」及「使用後產生哪些Effect」。
技能不得直接控制完整戰鬥流程。

36.天賦Schema

TalentDefinition{
id,
version,
tags[],
requirements[],
trigger_conditions[],
effects[],
rule_modifiers[],
resource_modifiers[],
status_modifiers[],
usage_limits[],
conflicts[],
ai_metadata
}
天賦應盡量透過Trigger、Effect與Modifier修改既有規則。
禁止大量建立「如果Talent_ID=X就在戰鬥核心加入特殊if」。

37.裝備Schema

EquipmentDefinition{
id,
version,
tags[],
slot_type,
requirements[],
base_modifiers[],
trigger_conditions[],
effects[],
granted_skills[],
learning_rules[],
special_rules[],
ai_metadata
}
裝備必須允許基礎數值與Build效果分離。
裝備特殊效果應優先使用通用Effect系統。

38.資源Schema

ResourceDefinition{
id,
version,
tags[],
scope,
initial_value_rule,
minimum,
maximum_rule,
generation_rules[],
consumption_rules[],
overflow_rule,
reset_rule,
conversion_rules[],
display_rule
}
scope至少能表達：永久、戰鬥、回合或其他必要生命週期。
所有資源變化必須產生正式事件。
不得直接在未知模組修改資源數值而不產生事件。

39.狀態Schema

StatusDefinition{
id,
version,
tags[],
duration_rule,
stack_rule,
max_stack_rule,
refresh_rule,
trigger_conditions[],
effects[],
remove_conditions[],
dispel_rules[],
conversion_rules[],
immunity_rules[],
ai_metadata
}
狀態持續時間、層數與移除規則必須明確。
不得依顯示文字推導實際效果。

40.EffectSchema

EffectDefinition{
id,
effect_type,
target_rule,
value_formula,
conditions[],
tags[],
resource_rule,
status_rule,
duration_rule,
stack_rule,
event_flags[],
follow_up_effects[]
}
Effect應成為技能、天賦、裝備、狀態、職業與敵人共用的效果語言。
優先增加通用Effect能力，而不是增加大量內容專用程式碼。

41.敵人Schema

EnemyDefinition{
id,
version,
tags[],
base_stats,
resource_refs[],
skills[],
passives[],
statuses[],
behavior_rules[],
phase_rules[],
mechanic_rules[],
reward_rules[],
ai_metadata
}
敵人與玩家角色應盡可能共用傷害、狀態、技能、事件、Effect等底層系統。
不得因敵人身分建立第二套完全不同的戰鬥引擎。

42.資料驗證

所有資料載入前必須執行Schema驗證。
至少檢查：
ID是否唯一。
引用ID是否存在。
必要欄位是否缺失。
標籤是否合法。
數值範圍是否合法。
最大值是否小於最小值。
Trigger是否引用合法Event。
Effect是否存在。
狀態層數是否合法。
資源上限是否合法。
是否存在明顯循環引用。
正式Build不得默默忽略錯誤資料。
開發模式應提供明確錯誤來源。

第二部分：戰鬥狀態機

43.狀態機原則

戰鬥核心必須由明確狀態機控制。
禁止以大量互相交錯的布林值控制戰鬥流程。
任何時刻戰鬥必須可以回答：
目前處於哪個Battle State？
目前正在處理哪個Action？
目前正在處理哪個Event？
下一個合法State是什麼？

44.頂層Battle State

概念狀態：
INITIALIZING
BATTLE_START
ROUND_START
TURN_ORDER
WAITING_ACTION
ACTION_PREPARE
ACTION_EXECUTION
EVENT_RESOLUTION
REACTION_RESOLUTION
ACTION_END
ROUND_END
VICTORY_CHECK
BATTLE_END
實際名稱依程式架構決定。
重點是狀態責任，而非名稱。

45.INITIALIZING

負責：
建立戰鬥實例。
載入參戰單位。
初始化資源。
初始化狀態。
初始化事件佇列。
初始化亂數Context。
建立戰鬥識別資料。
完成後進入BATTLE_START。

46.BATTLE_START

產生戰鬥開始事件。
處理戰鬥開始Trigger。
處理初始Effect。
處理衍生事件。
確認是否存在立即結束條件。
完成後進入ROUND_START。

47.ROUND_START

回合計數增加。
重置每回合Trigger限制。
重置回合型資源。
產生回合開始事件。
處理回合開始狀態、天賦、裝備、職業與其他效果。
處理死亡判定。
完成後進入TURN_ORDER。

48.TURN_ORDER

取得所有合法行動單位。
計算速度、優先度及其他順序修正。
產生穩定行動佇列。
相同條件不得依非穩定集合順序決定。
完成後進入WAITING_ACTION。

49.WAITING_ACTION

取得下一個可行動單位。
若無可行動單位，進入ROUND_END。
若為玩家控制，等待合法輸入。
若為AI控制，執行決策模組。
取得ActionCommand後進入ACTION_PREPARE。

50.ActionCommand

所有行動必須轉換成標準ActionCommand後才能進入戰鬥核心。
概念：
ActionCommand{
action_id,
actor_id,
action_type,
skill_id,
target_ids[],
input_metadata
}
UI不得直接呼叫傷害或技能Effect。
UI只能提交合法ActionCommand。

51.ACTION_PREPARE

檢查角色是否仍可行動。
檢查控制狀態。
處理行動前事件。
再次確認可行動性。
驗證技能。
驗證資源。
驗證冷卻。
驗證目標。
建立skill_cast_id。
支付成本。
完成後進入ACTION_EXECUTION。
若失敗，依失敗原因返回合法State。

52.ACTION_EXECUTION

建立技能使用事件。
解析目標。
解析Hit。
執行Effect。
每個Hit建立獨立hit_id。
產生相關Event。
若產生Trigger，轉入EVENT_RESOLUTION。
技能執行完成後不得直接跳至下一角色，必須先清空必要事件。

53.EVENT_RESOLUTION

取得事件佇列下一事件。
處理PRE。
處理MAIN。
處理POST。
收集Trigger。
建立TriggeredEffect。
依priority排序。
執行Effect。
產生衍生Event。
直到目前必要事件鏈完成。
如果產生Reaction，進入REACTION_RESOLUTION。

54.REACTION_RESOLUTION

處理反擊、中斷、保護、攔截等反應。
Reaction必須具有正式Action/Event資料。
不得直接插入任意函式。
反應完成後返回原事件處理流程。
系統必須限制Reaction連鎖深度與次數。

55.ACTION_END

確認所有直接效果完成。
確認必要事件鏈完成。
執行失去戰鬥能力判定。
執行行動後Trigger。
處理追加行動。
更新行動限制。
若戰鬥可能結束，進入VICTORY_CHECK；否則返回WAITING_ACTION。

56.ROUND_END

確認無未完成Action。
確認必要Event Queue為空。
處理回合結束事件。
處理持續效果。
更新狀態Duration。
移除到期狀態。
清除回合限定資料。
執行失去戰鬥能力判定。
進入VICTORY_CHECK。

57.VICTORY_CHECK

統一判斷戰鬥是否結束。
不得由技能自行宣布勝利或失敗。
若結束，進入BATTLE_END。
若未結束且本回合已完成，進入ROUND_START。
若戰鬥仍處於本回合合法流程，返回對應State。

58.BATTLE_END

停止接受一般ActionCommand。
處理戰鬥結束事件。
完成必要戰後效果。
產生戰鬥結果。
處理獎勵。
保存必要資料。
釋放Battle Context。

59.狀態轉移限制

每個State必須定義合法Next State。
非法轉移必須在開發模式報錯。
禁止任意模組直接修改currentBattleState。
Battle State只能由Battle State Machine控制。

60.暫停與恢復

狀態機應允許安全保存：
目前Battle State。
Round。
Action。
Event Queue。
Reaction Queue。
角色狀態。
資源。
Status。
Trigger計數。
亂數狀態。
若遊戲未規劃戰鬥中存檔，可暫不開放玩家使用，但架構不得依賴不可重建的隱性狀態。

第三部分：AI自動測試與平衡規格

61.測試目標

AI與自動測試的責任不是證明遊戲「絕對平衡」，而是主動尋找：
純上位技能。
永久無用技能。
單一最優Build。
無限循環。
無限行動。
無限資源。
異常爆發。
永久控制。
無敵循環。
事件死循環。
數值溢位。
敵人無解機制。
技能/天賦/裝備異常協同。

62.測試分層

至少建立：
單元測試。
資料驗證測試。
戰鬥整合測試。
事件鏈測試。
Build模擬測試。
敵人機制測試。
回歸測試。
壓力測試。
隨機模擬測試。

63.技能單元測試

每個技能至少測試：
合法目標。
非法目標。
成本足夠。
成本不足。
命中。
未命中。
暴擊。
非暴擊。
狀態成功。
狀態失敗。
多目標。
多段。
角色死亡。
目標死亡。
Trigger。
冷卻。
使用限制。
技能不得依UI才能正常執行。

64.天賦測試

每個天賦至少測試：
觸發條件成立。
觸發條件不成立。
每回合限制。
每場戰鬥限制。
標籤條件。
來源條件。
目標條件。
與其他天賦互動。
與裝備互動。
與狀態互動。
移除天賦後效果是否完全消失。

65.事件系統測試

至少測試：
父子Event關係。
root_event_id。
chain_depth。
priority。
PRE/MAIN/POST。
取消Event。
替代Event。
衍生Event。
多Trigger同時觸發。
相同priority穩定排序。
Event Queue清空。
Reaction Queue清空。
不得出現已resolved事件再次MAIN。

66.無限循環檢測

自動測試必須主動搜尋：
A觸發B→B觸發A。
A→B→C→A。
追加行動產生追加行動。
反擊觸發反擊。
治療觸發傷害→傷害觸發治療。
資源增加觸發資源增加。
狀態施加觸發同狀態施加。
系統必須存在MAX_CHAIN_DEPTH、每行動Trigger上限、每回合Trigger上限等安全機制。
觸發安全上限時必須留下完整事件鏈供除錯。

67.確定性測試

相同：
初始狀態。
玩家輸入。
資料版本。
亂數種子。
應產生相同戰鬥結果與事件順序。
此能力用於重現Bug與平衡分析。

68.Build模擬

測試工具應能建立大量合法Build組合並進行自動戰鬥。
每個Build至少記錄：
總傷害。
每回合平均傷害。
最高單回合傷害。
承受傷害。
治療量。
資源產生。
資源消耗。
資源溢出。
技能使用率。
技能勝率關聯。
狀態覆蓋率。
控制覆蓋率。
平均戰鬥回合。
死亡率。
事件觸發次數。

69.技能使用率分析

若某技能在大量合理Build與敵人環境中長期接近零使用率，不得立即直接Buff。
AI必須先分析：
是否存在純上位技能。
技能戰術用途是否不足。
成本是否過高。
是否缺乏相容天賦。
是否缺乏相容裝備。
是否缺乏適合敵人情境。
技能是否因UI或AI評估問題被忽略。
確認原因後才允許提出修改。

70.純上位檢測

自動比較用途相近技能。
若B在主要戰術維度全面不差於A且至少一項更優，標記Dominance Warning。
不得自動刪除或修改。
輸出：
被支配內容。
支配內容。
比較維度。
可能原因。
建議檢查方向。
由設計階段決定處理方式。

71.Build集中度

模擬大量Build後統計：
技能選擇率。
天賦選擇率。
裝備選擇率。
職業內Build分布。
若極少數組合長期支配大量不同敵人與情境，標記Build Concentration Warning。
高使用率本身不代表一定失衡，必須分析其是否因內容不足、AI偏差或真實數值優勢造成。

72.跨敵人測試

任何Build評估不得只對單一木樁目標測試。
測試集至少包含不同：
戰鬥長度。
敵人數量。
防禦模式。
速度。
狀態抗性。
爆發窗口。
資源壓力。
生存壓力。
戰術機制。
避免把單體DPS最高Build錯誤判定為全遊戲最佳Build。

73.敵人機制測試

每個重要敵人必須驗證：
是否至少存在多種合理處理方法。
是否存在唯一指定技能硬鎖。
是否可能形成永久無解狀態。
是否過度懲罰某類Build。
是否存在機制完全可以被無視。
是否存在預期外直接跳過機制的方法。
「可以被特殊Build克制」不等於Bug，但必須確認代價合理。

74.平衡修改原則

AI發現異常後不得直接以「降低傷害X%」作為預設解法。
修改順序優先檢查：
規則錯誤→Bug→事件錯誤→無限互動→成本→條件→敵人環境→標籤協同→資源循環→最後才是單純數值。
每次平衡修改必須記錄原因。

75.一次只改有限變數

進行平衡調整時應避免同時修改大量互相關聯數值。
每次調整應記錄：
修改前資料。
修改內容。
修改原因。
預
